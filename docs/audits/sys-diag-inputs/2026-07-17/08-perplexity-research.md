# Investigación: mejores prácticas multi-agente 2025-2026

**Alcance.** Este informe es investigación externa pura sobre prácticas, estándares y riesgos publicados; no describe ni infiere ningún stack, configuración ni infraestructura concreta de ninguna organización o usuario.

**Criterio de calidad de fuentes.** Se priorizan documentación oficial, estándares/proyectos, documentación de APIs y guías de seguridad reconocidas; cuando se usan blogs personales, preprints o investigación de proveedor, se marcan explícitamente como fuentes secundarias, preprints o de calidad/independencia menor.

## 1. Gobernanza multi-agente personal/PYME 2026

### Patrón recomendado: gateway + workers + supervisor humano

El patrón que emerge para equipos pequeños no es “un superagente autónomo”, sino un **plano de control ligero**: un gateway que centraliza identidad, permisos, políticas y auditoría; workers o agentes especializados con contratos explícitos; y un supervisor humano para aprobar acciones de alto impacto. Microsoft formula este principio como una baseline centralizada y exigible: “cada agente debe ser observable, gobernado y seguro”, con registro, identidad única y control de permisos ([Microsoft Learn, última actualización 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)).

Para evitar drift, cada agente debería tener una entrada de registro con propietario, propósito, plataforma, alcance de acceso, triggers, modelos/herramientas autorizadas, presupuesto y estado operativo; Microsoft recomienda registrar todo agente en un inventario organizacional único y rastrear ownership, purpose, platform y access scope ([Microsoft Learn, 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)). En la misma línea, los despliegues “shadow” se consideran riesgo de seguridad y coste, por lo que el antipatrón es permitir agentes no registrados o credenciales compartidas sin atribución individual ([Microsoft Learn, 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)).

El segundo control es **contrato de superficie**: qué entradas acepta el agente, qué herramientas puede invocar, qué outputs promete, qué datos puede leer/escribir y qué acciones requieren aprobación humana. MCP formaliza parte de ese contrato en roles host/client/server, mensajes JSON-RPC 2.0, negociación de capacidades y herramientas/recursos/prompts expuestos por servidores ([MCP Specification, versión 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18)). A2A complementa ese enfoque con “Agent Cards” para descubrimiento de capacidades, conexión y modalidades de interacción entre agentes opacos de proveedores distintos ([Google Developers Blog, 9-abr-2025](https://developers.googleblog.com/en/a2a-a-new-era-of-agent-interoperability/); [A2A GitHub README, release v0.3.0 visible 30-jul-2025](https://github.com/a2aproject/A2A)).

El tercer control es **autorización explícita de herramientas**: la especificación MCP exige que los hosts obtengan consentimiento explícito antes de invocar herramientas y advierte que las herramientas pueden representar ejecución arbitraria de código ([MCP Specification, 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18)). Para transportes HTTP, MCP evolucionó hacia OAuth 2.1, Protected Resource Metadata y discovery del authorization server, lo que convierte la autorización en parte del contrato entre cliente y servidor, no en una convención informal ([MCP Authorization, versión 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)).

El cuarto control es **observabilidad y auditoría antes de autonomía**. Microsoft recomienda identidad única para que las acciones de agentes sean atribuibles y aplicables a una identidad concreta, y recomienda lifecycle controls sobre permisos y ownership ([Microsoft Learn, 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)). En la práctica, esto implica logs de decisión/acción, trazas de tool calls, resultados, aprobaciones humanas, errores, costes y cambios de configuración, con retención proporcional al riesgo.

El quinto control es **kill-switch o pause-switch** por agente y por gateway. La documentación de gobernanza de proveedores no siempre usa la palabra “kill-switch”, pero el patrón operativo es pausar, deshabilitar o revocar identidad/permisos cuando un agente excede política, presupuesto o comportamiento esperado; Notion lo implementa para agentes de coste con pausa automática al agotarse créditos, y OpenAI describe pausas/confirmaciones antes de acciones sensibles en agentes de navegador ([Notion Releases, 5-may-2026](https://www.notion.com/releases/2026-05-05); [OpenAI, 7-nov-2025](https://openai.com/index/prompt-injections/)).

### Antipatrones ya claros

- **Agentes sin registro ni propietario**: Microsoft marca los despliegues “shadow” como riesgo de seguridad y coste ([Microsoft Learn, 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)).
- **Una sola identidad compartida para múltiples agentes o usuarios**: Microsoft exige identidad distinta por agente para atribución y enforcement ([Microsoft Learn, 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)).
- **Herramientas amplias sin consentimiento ni contrato**: MCP exige consentimiento explícito antes de tool invocation y advierte que las tools pueden equivaler a ejecución arbitraria ([MCP Specification, 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18)).
- **Prompt amplio tipo “haz lo que sea necesario” con acceso a email, documentos o web**: OpenAI advierte que dar instrucciones muy amplias puede dejar al agente con margen para seguir instrucciones dañinas ocultas en emails u otras fuentes ([OpenAI, 7-nov-2025](https://openai.com/index/prompt-injections/)).
- **Confiar solo en prompts de sistema como control de seguridad**: Anthropic afirma que ningún browser agent es inmune a prompt injection y que el problema sigue lejos de estar resuelto ([Anthropic, 24-nov-2025](https://www.anthropic.com/research/prompt-injection-defenses)).

## 2. Higiene de créditos Notion AI / agentes Notion 2026

### Controles oficiales de presupuesto

Notion documenta que los Custom Agents consumen Notion credits cada vez que ejecutan una tarea y que los créditos se comparten a nivel de workspace, por lo que el presupuesto debe administrarse como un saldo común y no por usuario aislado ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)). Los factores oficiales que aumentan consumo son cuánto lee el agente, cuántos pasos y tool calls realiza, con qué frecuencia corre y qué modelo se elige ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)).

Notion recomienda usar **Auto** para la mayoría de los casos, porque permite que Notion ajuste el modelo a la tarea, mientras que los modelos avanzados consumen más créditos por razonamiento más complejo ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)). La práctica de higiene es diseñar triggers, prompts y scopes para que el agente lea menos, llame menos herramientas y corra menos veces, antes de optimizar microcostes de modelo.

El 5 de mayo de 2026, Notion anunció controles administrativos para limitar quién puede crear agentes, establecer límites de crédito por agente y, en Enterprise, un límite de workspace para agentes nuevos y existentes ([Notion Releases, 5-may-2026](https://www.notion.com/releases/2026-05-05)). El mismo anuncio dice que el dashboard muestra uso total desglosado por agente, tendencias de gasto, estado y actividad reciente, y que los agentes se pausan si los créditos se agotan, evitando facturas sorpresa ([Notion Releases, 5-may-2026](https://www.notion.com/releases/2026-05-05)).

Notion también documenta notificaciones in-app y por email al 80% y 100% del uso, pausa automática de Custom Agents si no hay créditos suficientes, y disponibilidad inmediata de créditos adicionales si se aumentan a mitad del periodo mensual, con facturación al inicio del siguiente ciclo mensual ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)). En la misma página aparece una equivalencia de ejemplo “1,000 credits ($10)”, por lo que los equipos pequeños pueden convertir créditos a coste aproximado por ejecución y por mes ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)).

### Errores comunes de facturación y diseño

El primer error es asumir que el crédito pertenece al creador del agente; Notion dice que los créditos son compartidos por el workspace y que cada Custom Agent toma del mismo saldo sin importar quién lo creó o ejecutó ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)). El segundo error es tratar triggers frecuentes como gratis: Notion indica que agentes programados o disparados con frecuencia usan más créditos con el tiempo ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)).

El tercer error es usar modelos avanzados sin medición, porque Notion afirma que consumen más créditos y recomienda Auto para la mayoría de casos ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)). El cuarto error es comprar créditos en planes o canales no compatibles: Notion dice que Notion credits solo están disponibles en Business y Enterprise, y que si la suscripción se gestiona por Apple App Store o Google Play no se pueden comprar créditos desde Notion hasta migrar a un plan directo compatible ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)).

## 3. Patrones poller + worker sobre APIs SaaS: Notion y Slack

### Poller robusto: cursors, checkpoints e idempotencia

El patrón actual para pollers sobre SaaS es: guardar checkpoint persistente, usar cursors opacos, procesar por lotes pequeños, deduplicar por identificadores de evento/objeto, hacer writes idempotentes y respetar backoff del proveedor. Notion soporta paginación basada en cursor para endpoints de listas, devuelve por defecto 10 items por llamada, y usa `has_more`, `next_cursor`, `start_cursor` y `page_size` con máximo 100 ([Notion Developers, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/intro#pagination)).

Slack también usa cursor pagination en la mayoría de métodos paginados, con `response_metadata.next_cursor`; recomienda límites de 100-200 resultados por llamada, máximo 1000, y advierte que los cursors expiran y no deben persistirse durante horas o días ([Slack Developer Docs, sin fecha visible; consultado 17-jul-2026](https://docs.slack.dev/apis/web-api/pagination/)). Por eso, un checkpoint durable no debería ser solo “último cursor”, sino un estado semántico como último timestamp/event_id procesado, cola de pendientes y marca de última reconciliación.

La idempotencia debe implementarse fuera de la API cuando el proveedor no ofrece claves idempotentes por operación: Notion webhooks incluyen `id` del evento, `timestamp` y `attempt_number` de 1 a 8, mientras Slack Events API incluye `event_id` globalmente único y `event_time` ([Notion Webhook Delivery, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/webhooks-events-delivery); [Slack Events API, sin fecha visible; consultado 17-jul-2026](https://docs.slack.dev/apis/events-api/)). Un worker prudente registra “seen events” y “processed side effects” antes o dentro de una transacción idempotente, de modo que reintentos o procesamiento parcial no dupliquen mensajes, escrituras o gastos.

### Backoff y rate limits documentados

Notion aplica dos rate limits: por conexión, con promedio de tres requests por segundo y algunos bursts, y por workspace, compartido por las conexiones del workspace y escalado según plan ([Notion Request Limits, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/request-limits)). Cuando se exceden límites, Notion devuelve `rate_limited` con HTTP 429, usa `additional_data.rate_limit_reason` para indicar la razón, y recomienda manejar HTTP 429 y 529 respetando `Retry-After` como número entero de segundos ([Notion Request Limits, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/request-limits)).

Slack aplica límites por método, workspace/team y app, organiza Web API en tiers desde 1+ hasta 100+ requests por minuto, y devuelve HTTP 429 con `Retry-After` cuando un método supera la ventana aplicable ([Slack Rate Limits, cambio visible 29-may-2025](https://docs.slack.dev/apis/web-api/rate-limits)). Slack además indica que usar cursored pagination otorga mejores condiciones de rate limiting, mientras que no usar paginación puede aplicar límites más estrictos ([Slack Rate Limits, cambio visible 29-may-2025](https://docs.slack.dev/apis/web-api/rate-limits)).

El antipatrón de polling es ignorar `Retry-After`, usar loops fijos de alta frecuencia o lanzar workers paralelos sin coordinación por workspace. La práctica recomendada es un token bucket por proveedor/workspace/método, colas con jitter, backoff exponencial solo después de honrar `Retry-After`, y presupuesto separado para reconciliaciones lentas.

### Cuándo migrar de polling a webhooks/event delivery

Debe migrarse de polling a webhooks cuando el caso necesita reacción cercana a tiempo real, reduce lectura repetitiva, o el proveedor entrega eventos fiables con firma y reintentos. Notion webhooks envían POST seguro cuando cambian páginas o bases de datos, requieren endpoint público con SSL, y cada request incluye `X-Notion-Signature` con HMAC-SHA256 firmado usando `verification_token` ([Notion Webhooks, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/webhooks)).

Sin embargo, Notion webhooks no reemplazan por completo la lectura: la documentación dice que los eventos no contienen el contenido completo cambiado y que la conexión debe llamar a la API para recuperar el estado más reciente ([Notion Webhook Delivery, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/webhooks-events-delivery)). Notion también advierte que los eventos pueden llegar en orden distinto, pueden no mostrar el estado más actual, y recomienda usar el timestamp para reordenar y hacer fetch de los datos más recientes ([Notion Webhook Delivery, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/webhooks-events-delivery)).

Slack Events API es apropiada cuando “Slack calls you”: Slack entrega un HTTP POST por evento, exige responder HTTP 2xx en tres segundos, reintenta tres veces con backoff exponencial y puede deshabilitar entregas si la tasa de éxito cae por debajo de 5% en 60 minutos para apps con volumen suficiente ([Slack Events API, sin fecha visible; consultado 17-jul-2026](https://docs.slack.dev/apis/events-api/)). Por tanto, el patrón event-driven correcto es ACK rápido, persistir el evento, encolar trabajo, deduplicar por `event_id`, y procesar asincrónicamente.

La migración ideal no es “webhooks o polling”, sino **webhook como señal + poller de reconciliación**. Notion lo exige de facto porque el webhook es una señal y no el estado completo, y Slack lo sugiere operativamente al separar recepción rápida y procesamiento para evitar timeouts y deshabilitación ([Notion Webhook Delivery, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/webhooks-events-delivery); [Slack Events API, sin fecha visible; consultado 17-jul-2026](https://docs.slack.dev/apis/events-api/)).

## 4. Riesgos de gateways self-hosted tipo OpenClaw / computer-use 2025-2026

### Superficies de ataque conocidas

La superficie central de los agentes con browser/computer-use es que consumen contenido no confiable y actúan con autoridad delegada. OpenAI define prompt injection como ingeniería social específica de IA conversacional y señala que puede ocultarse en web, documentos o email ([OpenAI, 7-nov-2025](https://openai.com/index/prompt-injections/)). Anthropic afirma que cada página web visitada por un agente es un vector potencial, que resultados, documentos y aplicaciones legítimas pueden contener instrucciones maliciosas, y que ningún browser agent es inmune a prompt injection ([Anthropic, 24-nov-2025](https://www.anthropic.com/research/prompt-injection-defenses)).

En gateways self-hosted, la exposición se amplía porque el gateway suele ser control plane, broker de mensajes, puente a herramientas y punto de entrada de canales. La documentación oficial de OpenClaw —fuente oficial pero **sin fecha visible**— advierte que un gateway/agent compartido por usuarios mutuamente no confiables no está soportado, y que varios usuarios no confiables que pueden mensajear un agente con herramientas comparten la autoridad delegada de ese agente ([OpenClaw Security Docs, sin fecha visible; consultado 17-jul-2026](https://docs.openclaw.ai/gateway/security)).

La misma documentación de OpenClaw advierte que el Gateway multiplexa WebSocket y HTTP en un puerto, que no debe exponerse sin autenticación en `0.0.0.0`, y que credenciales para endpoints como chat completions, responses, admin RPC o channels son secretos de operador full-access ([OpenClaw Security Docs, sin fecha visible; consultado 17-jul-2026](https://docs.openclaw.ai/gateway/security)). También advierte que el Control UI puede deshabilitar checks de identidad mediante configuraciones peligrosas, y que `allowedOrigins: ["*"]` es una política allow-all explícita, no un default endurecido ([OpenClaw Security Docs, sin fecha visible; consultado 17-jul-2026](https://docs.openclaw.ai/gateway/security)).

La gestión de secretos es una superficie crítica: la documentación de OpenClaw dice que archivos bajo `~/.openclaw/` o `$OPENCLAW_STATE_DIR/` pueden contener secretos o datos privados, que `openclaw.json` puede incluir tokens, que SQLite de estado puede incluir OAuth access/refresh tokens, y que transcripts/logs pueden contener secretos pegados, outputs de comandos y URLs ([OpenClaw Security Docs, sin fecha visible; consultado 17-jul-2026](https://docs.openclaw.ai/gateway/security)). La mitigación estándar es mínimo privilegio, redacción de logs, patrones custom para tokens/hostnames/internal URLs, separación por usuario/host y no compartir credenciales de operador con callers no confiables ([OpenClaw Security Docs, sin fecha visible; consultado 17-jul-2026](https://docs.openclaw.ai/gateway/security)).

### Incidentes y evidencia pública

**Fuente preprint.** Un preprint de arXiv sobre browsing agents reportó que Browser Use fue vulnerable a prompt injection, bypass de validación de dominio y exfiltración de credenciales, con CVE-2025-47241 y remediación en versión 0.1.45; al ser preprint, debe tratarse como evidencia técnica no revisada por pares ([arXiv, 19-may-2025](https://arxiv.org/html/2505.13076v1)). El mismo preprint recomienda defensa en profundidad con sanitización, separación planner-executor, analizadores formales, sandboxing, tokenización de autenticación y revocación de credenciales ([arXiv, 19-may-2025](https://arxiv.org/html/2505.13076v1)).

**Fuente preprint sobre OpenClaw.** Un preprint de arXiv afirma haber sistematizado 470 advisories contra OpenClaw entre enero y abril de 2026, con superficies como Gateway WebSocket, Channel Input Interface, Tool Dispatch, Exec Policy Engine y Container Boundary; al ser preprint, se marca como evidencia secundaria no oficial y no como confirmación regulatoria ([arXiv, 13-may-2026](https://arxiv.org/html/2603.27517v3)). Ese preprint describe riesgos concretos como WebSocket en puerto 18789, tokens enviados durante handshake a endpoints controlados por atacante, Slack payloads sin sanitización, Telegram bot tokens en DEBUG y sandbox Docker dependiente de configuración runtime ([arXiv, 13-may-2026](https://arxiv.org/html/2603.27517v3)).

**Fuente de proveedor.** Acronis Threat Research Unit describe OpenClaw como asistente local con interfaces WhatsApp, Telegram, Slack, Discord o iMessage y Control UI local, y señala que el Gateway expone una interfaz WebSocket en TCP/18789 pensada para acceso local o túneles seguros, no Internet directo ([Acronis TRU, 23-feb-2026](https://www.acronis.com/en/tru/posts/openclaw-agentic-ai-in-the-wild-architecture-adoption-and-emerging-security-risks/)). Acronis también reporta que Censys observó crecimiento de unas 1,000 a más de 21,000 instancias expuestas públicamente en menos de una semana, por lo que esta cifra debe leerse como hallazgo de proveedor que cita a Censys, no como métrica oficial del proyecto ([Acronis TRU, 23-feb-2026](https://www.acronis.com/en/tru/posts/openclaw-agentic-ai-in-the-wild-architecture-adoption-and-emerging-security-risks/)).

**Fuente de proveedor/medio técnico, calidad secundaria.** NSFOCUS reporta CVE-2026-25253 para modificación de gateway y CVE-2026-25157 para command injection, además de casos descubiertos por usuarios o investigadores; se marca como fuente secundaria de proveedor y debe verificarse contra bases oficiales si se usa para decisiones de cumplimiento ([NSFOCUS Global, 12-feb-2026](https://nsfocusglobal.com/openclaw-open-source-ai-agent-application-attack-surface-and-security-risk-system-analysis/)).

### Mitigaciones estándar

Las mitigaciones convergen en cinco capas. Primero, **aislar contexto no confiable** mediante delimitación, provenance tags y escaneo de tool outputs; OpenAI menciona jerarquía de instrucciones y monitores automáticos, y Anthropic menciona escaneo de contenido no confiable en la ventana de contexto ([OpenAI, 7-nov-2025](https://openai.com/index/prompt-injections/); [Anthropic, 24-nov-2025](https://www.anthropic.com/research/prompt-injection-defenses)). Segundo, **reducir privilegio** mediante logged-out mode, perfiles dedicados y confirmaciones humanas para acciones sensibles como compras o envío de email ([OpenAI, 7-nov-2025](https://openai.com/index/prompt-injections/)).

Tercero, **aislar ejecución** con sandbox, contenedores validados, denylist de paths sensibles y sin network host por defecto; el preprint de Browser Use recomienda sandboxing browsers y aislamiento estricto de credenciales, mientras la documentación de OpenClaw recomienda sandboxing y host isolation para límites fuertes ([arXiv, 19-may-2025](https://arxiv.org/html/2505.13076v1); [OpenClaw Security Docs, sin fecha visible; consultado 17-jul-2026](https://docs.openclaw.ai/gateway/security)). Cuarto, **endurecer gateway/control UI** con auth obligatoria, TLS, allowed origins estrictos, no exposición pública directa y separación por OS user/host para usuarios no confiables ([OpenClaw Security Docs, sin fecha visible; consultado 17-jul-2026](https://docs.openclaw.ai/gateway/security)). Quinto, **gobernar supply chain de skills/plugins** mediante revisión, signing, allowlists y scanning, recomendación que Acronis formula para OpenClaw y que aplica de forma general a agentes con plugins ejecutables ([Acronis TRU, 23-feb-2026](https://www.acronis.com/en/tru/posts/openclaw-agentic-ai-in-the-wild-architecture-adoption-and-emerging-security-risks/)).

## 5. Checklist de 10 puntos: estado del arte 2026

| # | Control | Criterio de evaluación |
|---:|---|---|
| 1 | Registro único de agentes | Todo agente tiene owner, propósito, plataforma, identidad, permisos, triggers, coste y estado; no hay agentes “shadow” ([Microsoft Learn, 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)). |
| 2 | Identidad y permisos por agente | Cada agente opera con identidad distinta y permisos mínimos, no credenciales compartidas ([Microsoft Learn, 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)). |
| 3 | Contratos de superficie | Tools, recursos, prompts, inputs, outputs y capabilities están definidos con schemas/Agent Cards/MCP contracts ([MCP Spec, 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18); [A2A GitHub, release visible 30-jul-2025](https://github.com/a2aproject/A2A)). |
| 4 | Human-in-the-loop real | Acciones sensibles tienen confirmación o pausa, y el usuario puede revisar antes de compras, emails o cambios irreversibles ([OpenAI, 7-nov-2025](https://openai.com/index/prompt-injections/)). |
| 5 | Kill-switch y budget-switch | Se puede pausar/deshabilitar agente por coste, anomalía, política o incidente; los agentes de coste tienen límites y alertas ([Notion Releases, 5-may-2026](https://www.notion.com/releases/2026-05-05)). |
| 6 | Auditoría y observabilidad | Se registran tool calls, decisiones, aprobaciones, errores, identidades, costes y cambios de configuración ([Microsoft Learn, 26-jun-2026](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ai-agents/governance-security-across-organization)). |
| 7 | Higiene de créditos | Triggers están limitados, modelos avanzados se justifican, dashboards se revisan y Auto es default salvo evidencia contraria ([Notion Help, sin fecha visible; consultado 17-jul-2026](https://www.notion.com/help/buy-and-track-notion-credits-for-custom-agents)). |
| 8 | Poller/event-worker resiliente | Cursors opacos, checkpoints semánticos, dedupe, ACK rápido, backoff con `Retry-After` y reconciliación periódica están implementados ([Notion Request Limits, sin fecha visible; consultado 17-jul-2026](https://developers.notion.com/reference/request-limits); [Slack Events API, sin fecha visible; consultado 17-jul-2026](https://docs.slack.dev/apis/events-api/)). |
| 9 | Gateway endurecido | Gateway/Control UI no está expuesto sin auth, tiene TLS/origins estrictos, secretos protegidos y aislamiento por usuario/host ([OpenClaw Security Docs, sin fecha visible; consultado 17-jul-2026](https://docs.openclaw.ai/gateway/security)). |
| 10 | Defensa contra prompt injection multicanal | Web, docs, email, canales, logs y tool outputs se tratan como no confiables; se usan provenance tags, scanners, sandbox y privilegio mínimo ([OpenAI, 7-nov-2025](https://openai.com/index/prompt-injections/); [Anthropic, 24-nov-2025](https://www.anthropic.com/research/prompt-injection-defenses)). |

## Conclusión

El “estado del arte 2026” para sistemas multi-agente personales o de PYME es menos una arquitectura compleja que una disciplina de control: inventario, identidad, contratos, límites, auditoría y reversibilidad. MCP y A2A estandarizan interfaces y descubrimiento; OWASP, NIST/CSA y guías de proveedor ayudan a estructurar riesgo; Notion y Slack muestran cómo costes, rate limits y event delivery obligan a diseñar presupuestos, backoff e idempotencia desde el inicio. El antipatrón común en todas las áreas es delegar autoridad amplia a agentes sin registro, sin presupuesto, sin superficie contractual, sin sandbox y sin intervención humana verificable.
